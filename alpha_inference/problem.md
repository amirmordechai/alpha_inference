# GenAI Inference, Quantization, Speculative Decoding & GPU Kernel Optimization on vLLM

Evolve `get_candidate_config()` inside `candidate.py` to optimize live `vLLM` inference performance on a real 1:1 production request trace while passing the strict Layer-2 Token-Logprob KL Output-Equivalence Gate (`<= 1%` distribution drift vs. the Ground-Zero `BF16` baseline).

## Hard Contract (Never Violate)
1. **Do NOT rename `get_candidate_config()`** or remove required returned dictionary keys:
   - Required keys: `plain_title` (short <=48-char human summary, no raw CLI flags), `hypothesis`, `category` (`vllm_flags` | `cuda_graphs` | `backends` | `triton_kernels`), `vllm_args` (`list[str]`), `env_vars` (`dict[str, str]`), `custom_kernel_code` (`str`).
   - Optional hardware MoE schedule key: `moe_tuned_config` (`dict[int, dict[str, int]]`, mapping token batch bucket `M` -> Triton tile dict).
2. **Immutable Model Checkpoint & Context Window:** Keep the exact model ID (`vllm_args[0]`), `--served-model-name`, `--max-model-len >= baseline`, and `--max-logprobs >= 5`. Never swap checkpoints, pass `--load-format=dummy`, or reference external HuggingFace draft models.
3. **Deterministic Container Compatibility Guards (`vLLM v0.31+` / CUDA 13):**
   - Do not pass `--disable-log-requests` (removed in `vLLM v0.31+`; use `--disable-uvicorn-access-log`).
   - Do not set `CUDA_MODULE_LOADING="EAGER"` (triggers multi-minute PTX JIT stalls) or `PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"` (conflicts with `vLLM` CUDA graph memory pools).
4. **Scientific Incremental Co-Design:** Mutate **1 to 2 orthogonal levers at a time** from the fastest working parent program, using the live `Engine Internals` telemetry (`ITL ms/tok`, `TTFT`, `QueueWait`, `Prefill`, `Decode`, `SpecAccept`, `Top GPU CUDA Kernels`) to target the true bottleneck.

## Hardware-Aware & Low-Level Optimization Search Space
1. **`backends` (Hardware `FP8` Quantization, Attention & Low-Level Kernel Dispatch):**
   - **Online Hardware `FP8` Weights & KV Cache (Blackwell / Hopper Tensor Cores):** Explore `--quantization=fp8` (online dynamic `BF16` -> `FP8` quantization of linear & MoE expert weights, cutting weight memory traffic in half and unlocking `fp8_w8a8` Tensor Core kernels) and/or `--kv-cache-dtype=fp8` (or `fp8_e4m3`, optionally paired with `--calculate-kv-scales`). Note: if a checkpoint has mixed `head_dim > 256` global attention layers that conflict with `flashinfer` + `fp8` KV cache, test `--quantization=fp8` with `BF16`/`auto` KV cache first, or pair `fp8` KV cache with compatible `--attention-backend` (`FLASH_ATTN` / `TRITON_ATTN` / `auto`). Every candidate is automatically verified by the Layer-2 KL gate.
   - **Kernel Backend Selection (`--kernel-config` JSON):** Pass `--kernel-config='{"moe_backend":"...","linear_backend":"...","enable_flashinfer_autotune":true}'` to test hardware-specialized dispatchers (`moe_backend`: `"auto"`, `"triton"`, `"batched_triton"`, `"cutlass"`, `"flashinfer_trtllm"`, `"flashinfer_cutlass"`, `"b12x"`, `"marlin"`; `linear_backend`: `"auto"`, `"b12x"`, `"flashinfer_cutedsl"`, `"cutlass"`, `"marlin"`, `"triton"`).
   - Also tune `--attention-backend` (`FLASHINFER`, `FLASH_ATTN`, `TRITON_ATTN`), `VLLM_USE_V2_MODEL_RUNNER`, `TOKENIZERS_PARALLELISM`, and `OMP_NUM_THREADS`.
2. **`vllm_flags` (Self-Contained Speculative Decoding & Continuous-Batching Co-Adaptation):**
   - **GPU N-Gram Speculative Decoding (`--speculative-config` JSON):** On **unconstrained text workloads** (when requests do **not** pass API-level `response_format` `json_schema`/`json_object` or `tools` guided decoding, which conflicts with XGrammar FSM rollbacks under load in `vLLM v0.31.0`), test zero-VRAM GPU n-gram speculation:
     `--speculative-config='{"method":"ngram_gpu","num_speculative_tokens":2,"prompt_lookup_max":4,"prompt_lookup_min":2}'` (or `"method":"ngram"`, tuning `num_speculative_tokens` in `2..4` and `prompt_lookup_max/min`). Check `SpecAccept` and `ITL` in telemetry to verify net speedup at high concurrency.
   - **Scheduler Co-Adaptation:** Once `FP8`, MoE tiles, or kernels reduce per-step GPU time, re-tune `--max-num-batched-tokens` (`2048`..`8192`), `--long-prefill-token-threshold` (`512`..`4096`), `--max-num-seqs` (`128`..`384` — never starve high-load concurrency!), `--block-size` (`16`, `32`, `64`), `--gpu-memory-utilization` (`0.92`..`0.96`), `--async-scheduling`, and `--language-model-only` (if serving text-only traces on a multimodal checkpoint).
3. **`cuda_graphs` (`--compilation-config` & `moe_tuned_config` Triton Tile Schedules):**
   - **Hardware-Specific `fused_moe` Triton Tile Schedules (`moe_tuned_config`):** `vLLM` often lacks hand-tuned MoE JSON tables for newer GPUs or specific `(E, N)` shapes, falling back to generic `BLOCK_SIZE_M=64, BLOCK_SIZE_N=128` defaults. For sparse MoE models (e.g., `E=128, top_k=8`), `tokens_per_expert = M * top_k / E` is only `~8–16` even at `M=128..256` concurrent requests, wasting >75% of `BLOCK_SIZE_M=64` tiles on zero padding! Return `"moe_tuned_config"` mapping batch buckets `{1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024}` to dicts with:
     `BLOCK_SIZE_M` (`16`, `32`, `64`), `BLOCK_SIZE_N` (`32`, `64`, `128` — prefer exact divisors of `moe_intermediate_size`!), `BLOCK_SIZE_K` (`64`, `128`, `256`), `GROUP_SIZE_M` (`1`, `8`, `16`, `32`), `num_warps` (`4`, `8`), `num_stages` (`3`, `4`, `5`). (Note: `moe_tuned_config` takes effect when MoE runs on the Triton backend, e.g. `moe_backend="triton"` or `"auto"` selecting Triton.)
   - **CUDA Graph Capture Ladders (`--compilation-config` JSON):** Tune `cudagraph_capture_sizes` (e.g. dense capture across active decode batch sizes `1..256`) and `max_cudagraph_capture_size` (`256`, `512`, `1024`) in `--compilation-config` (avoid deprecated `"level"` keys in `vLLM v0.31+`).
4. **`triton_kernels` (`custom_kernel_code` via `sitecustomize.py` & `register_vllm_patch`):**
   - `sitecustomize.py` provides `register_vllm_patch(module_name, patch_fn)` so your `@triton.jit` kernels patch target `vLLM` model classes cleanly inside `EngineCore` GPU worker processes right before model instantiation and CUDA graph capture!
   - Inspect the live target model layer source in `Active Experiment Context` and fuse memory-bound eager op chains into single-pass `@triton.jit` kernels computed in `tl.float32` and cast back to `x.dtype` (for example: fusing unweighted `RMSNorm` + `root_size` + learned `scale` multiplies inside custom MoE `Router.forward`, or fusing post-attention / post-feedforward `RMSNorm` + residual addition + `layer_scalar` multiplication). Always keep exact mathematical semantics so KL divergence stays `<= 0.03`, wrap patches defensively, and never import network or subprocess modules.
